PURPOSE
==============================================================================

This document defines the end-to-end onboarding experience for installing
Payment Connectors within the Lekki Platform.

The objective is to hide technical complexity while allowing highly flexible
enterprise payment configurations.

The onboarding experience should feel simple enough for a small restaurant,
yet powerful enough for multi-national hospitality groups.

The business should feel like they are configuring "Payments", not installing
software.

==============================================================================

UX PRINCIPLES
==============================================================================

The onboarding experience should

• Be guided
• Require minimal technical knowledge
• Validate continuously
• Explain every decision
• Never expose implementation details
• Save progress automatically
• Be reversible
• Support single and multi-venue businesses

5. Architectural Quality Attribute ValidationThe architectural design in LEK-022 satisfies several critical system properties:  Security (Least Privilege): The Pilot SDK operates within an isolated sandbox. It has zero access to database connections or other integrations. It only interacts with the platform via standard APIs using key credentials injected into memory at boot.  Loose Coupling (Decoupling): Core modules (Billing, Ordering) never call Pilot explicitly. They only publish an event asking for a provider that supports CreatePayment. The platform runtime resolves the route dynamically based on the venue's active configuration.  Zero Configuration Overload: The restaurant operator sees clean, business-oriented screens ("Where should your funds go?") rather than complex code configurations. The platform dynamically reads the integration manifest to generate the matching fields and connections automatically.
