The verdict
This is better than most skill systems I read. The descriptions follow a real formula — own a domain, say when to use it, list the words a human would actually type, name what it is not for, point at the sibling skill. The bodies are a genuine procedure (When / Do / Never / Handoff / Read), they stay at 30–50 lines, and they carry Lekki-specific law rather than generic advice. Every path they reference resolves.

The gap is not that testing was absent — it is that the skills were blind to it. This repo has 17 test files using node:test with a .test.ts convention, and apps/runtime/package.json wires money.test.ts and settlement.test.ts into its test script. Yet not one of the 26 skills contains unit test, node:test or .test.ts, and qa-architect defines done as browser E2E plus an HCI score. An agent following the skills would open a browser rather than add a case to a file that already exists.

So the skill system could neither direct anyone to the existing practice nor tell them which invariants remained unproven. The fix is small and specific: two new skills and one honest edit to qa-architect. Everything else below is polish on something that already works.

Start here

The three that are structural
These are not gaps in polish. Each one means the skill system cannot catch a class of failure that is live in your codebase right now.

1
No skill anywhere mentions a unit test

A grep across all 26 skills for unit test, vitest, jest, node:test or .test.ts returns nothing. qa-architect — the file that owns the quality gate — defines done as: build clean, exercise the journey in a browser, capture evidence, hold the HCI score. Every one of those is integration-level. Meanwhile money.test.ts and settlement.test.ts already exist and already run. The skills cannot point at them, cannot tell an agent to extend them, and cannot say which invariants they leave uncovered — so the practice survives on whoever remembers it rather than on the system.

Fix
Add money-invariants (drafted below) and give qa-architect a unit-test tier above its browser tier.
2
Nothing owns the proof, only the law

payments-architect is a good skill. It states the law — allocations, splits, tips, refunds, connectors behind a capability, basis-points integer math. What it does not do, and what no sibling does, is say what must be true and how you would know. There is a difference between "use integer math" and "a R100 bill split three ways must settle to exactly zero, and here is the test that proves it." The first is a design rule. The second is an invariant. You have the first everywhere and the second nowhere.

Fix
Invariants belong in references/ as a table of cases, loaded on demand. Draft below.
3
qa-architect contradicts itself in nine lines

Do step 1 reads "Build clean (no new TS/Angular warnings you introduced)." Never reads "Approve because it compiles." Those are the same claim with opposite signs, sitting eleven lines apart in the file that decides whether work ships. An agent resolving that conflict will pick whichever is cheaper, which is the compiler. Compiling is table stakes, not a gate — it does not belong in the Do list at all.

Fix
Delete Do #1. A clean build is a precondition for running the gate, not a step in it.

Concrete

The skill I would write first
Not a template — the actual file. Its value is the invariant table, which is the thing that currently exists nowhere in your repository.

.cursor/skills/qa/money-invariants/SKILL.md
---
name: money-invariants
description: >-
  Proves Lekki money arithmetic: splits, tips, settlement, rounding, minor units.
  Use before merging anything touching payments, transactions, Decimal columns,
  toMinor, split or settle. Triggers: split bill, equal share, tip, settle,
  rounding, cents, Decimal, does the maths work. Write the test, then the fix.
paths:
  - "apps/runtime/src/leos/**"
  - "prisma/schema.prisma"
---

# Money invariants

## When

Any change to money storage, arithmetic, allocation, settlement or refunds.

## Do

1. Write the failing test first. Money changes land test-first, no exceptions.
2. Assert against the table in `references/invariants.md`.
3. Money is `Decimal(12,2)` at rest, integer minor units in arithmetic.
   Never float, never an epsilon comparison.
4. Every allocation must sum back to the total. Prove it, do not reason it.
5. Concurrency counts: two payers racing is a test, not an edge case.

## Never

Approve money on a browser screenshot · compare with a tolerance ·
round mid-calculation · trust a client-supplied amount.

## Handoff

Design law → `payments-architect`. Schema → `data-architect`.
Journey evidence → `qa-architect`.
references/invariants.md — the part that matters
| # | Invariant                          | Case                    | Must hold        |
|---|------------------------------------|-------------------------|------------------|
 1   Equal split settles to zero        R100 ÷ 3                  sum == 100.00
 2   Last payer inherits no remainder   R100 ÷ 3, pay in order    3rd owes 33.34
 3   Multi-transaction visit            starters 200 + mains 150  quoted == charged
 4   Tip computed on server base        15% on a 2-tx visit       tip == 15% of 350
 5   Concurrent full payment            two payers, same instant  total charged 350
 6   Divisor excludes non-orderers      4th guest scans, no order share stays 1/3
 7   Stale participant secret           yesterday's secret        rejected, 400
 8   Settled bill rejects new payment   pay twice                 second refused
 9   Decimal boundary                   33.333 → storage          never widens
10   Refund path exists                 request a refund          not a silent stub
Rows 1 and 3 are already covered by money.test.ts and settlement.test.ts. Rows 2 and 9 are partial — the arithmetic is asserted, the allocation logic that produces it is not. Rows 4–8 and 10 (tip base, concurrency, non-orderers, stale secrets, double-pay, refunds) have never been executed against an assertion. The table's job is to make that distinction visible, which nothing in the repo currently does.

Mechanical fixes
None of these change what a skill says. All of them change whether it fires, or whether your tooling can read it.

Normalise line endings

Your 24 authored skills are CRLF; the 2 imported kits are LF. Harmless to Cursor, fatal to any script that matches ^---$ — it broke my extraction twice before I noticed. One line in .gitattributes: *.md text eol=lf.

studio, experience, operate, growth to their page trees; data-architect to prisma/**; security-architect to the auth tree. Precision costs one frontmatter key.

The description formula. Own a domain · use-when · literal trigger words · what it is not for · which sibling instead. Every one of the 24 you wrote follows it. That is the single hardest part of skill authoring and it is done.
When / Do / Never / Handoff / Read. A numbered Do, a middot-separated Never, and typed handoffs that name the next skill. It fits on one screen and it is the same shape every time, so an agent knows where to look.
voice.md. Register per surface with a real line for each, and prefer/avoid pairs naming the banned words. Most brand guidelines are adjectives; this one is usable.
The README taxonomy. Rules / skills / agents / craft kits, each with when it loads. Very few teams write down the difference between an agent and a skill, and the ones that do not end up with both doing neither.
Encoded bug knowledge. angular-web items 7 and 8 are lessons from real incidents, written as law. That is the highest-value content a skill can hold and it is the clearest evidence these were written from work rather than from a template.
Gating the imported kits by description. Naming Guest / Studio / Operate / Grow as out of scope for the Awwwards kit is the right instinct — the kit would otherwise happily put GSAP in the guest shell.
