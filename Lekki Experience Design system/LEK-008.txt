==============================================================================
PURPOSE
==============================================================================

This document defines the Event-Driven Architecture (EDA) strategy for the
Lekki platform.

Events are the primary mechanism by which business capabilities communicate.

Rather than directly calling one another whenever possible, platform modules
publish business events describing what has already occurred.

Other modules subscribe to these events and react independently.

This approach reduces coupling, improves scalability, simplifies integrations,
supports offline synchronisation and enables Neo to observe platform activity
without interfering with operational workflows.

==============================================================================
WHY EVENT-DRIVEN ARCHITECTURE?
==============================================================================

Traditional enterprise systems often rely on direct service-to-service calls.

Example

Guest places an order

↓

Ordering Service

↓

Billing Service

↓

Inventory Service

↓

Kitchen Service

↓

Analytics Service

↓

Notification Service

↓

Neo

Each service depends directly on several others.

As the platform grows these dependencies become increasingly complex.

Every new feature requires modifying existing services.

The platform becomes fragile.

Lekki adopts an event-first architecture instead.

==============================================================================
THE CORE PRINCIPLE
==============================================================================

Services should announce what happened.

They should never decide who needs to know.

Example

Order Submitted

Instead of calling

Kitchen

Analytics

Neo

Billing

Notifications

the Ordering Context simply publishes

OrderSubmitted

Interested modules react independently.

==============================================================================
EVENT CHARACTERISTICS
==============================================================================

A business event always represents something that has already happened.

Correct examples

SessionStarted

ParticipantJoined

VenueOpened

OrderSubmitted

OrderPrepared

BillCreated

BillSplit

PaymentAuthorised

PaymentCompleted

VenueClosed

NeoRecommendationAccepted

Incorrect examples

CreateOrder

SendNotification

UpdateInventory

ProcessPayment

These are commands.

Not events.

Commands request work.

Events describe completed work.

==============================================================================
EVENT DESIGN PRINCIPLES
==============================================================================

Events should be

Immutable

Past tense

Business focused

Self-contained

Versioned

Auditable

Never deleted

Events become part of the permanent business history.

==============================================================================
CORRELATION IDs
==============================================================================

Every business workflow should share a Correlation ID.

Example

Guest scans QR

↓

Session Created

↓

Order Submitted

↓

Bill Created

↓

Payment Completed

All events can be reconstructed using the same Correlation ID.

This dramatically improves observability and troubleshooting.

==============================================================================
EVENT VERSIONING
==============================================================================

Events evolve over time.

Old consumers should continue operating.

Rules

Never remove existing fields.

Only add optional fields.

Publish new versions when breaking changes occur.

Support migration windows.

Events are public contracts.

Treat them accordingly.

==============================================================================
EVENT STORAGE
==============================================================================

Important business events should be retained.

Benefits

Audit history

Analytics

Compliance

Neo learning

Operational replay

Customer support

Historical reporting

The event history becomes the operational memory of the platform.

==============================================================================
OFFLINE SYNCHRONISATION
==============================================================================

Offline behaviour naturally aligns with events.

While offline

Events are queued locally.

When connectivity returns

Events are replayed.

The platform converges automatically.

This greatly simplifies offline architecture.

==============================================================================
NEO AS AN EVENT SUBSCRIBER
==============================================================================

Neo should never require direct integration with business modules.

Neo subscribes to business events.

Examples

Venue performance

Order delays

Payment failures

Guest behaviour

Configuration changes

Neo observes.

Neo learns.

Neo recommends.

Neo does not interfere with operational workflows.

==============================================================================

External systems should integrate through events whenever possible.

Examples

This reduces direct dependencies between systems.

==============================================================================
OBSERVABILITY
==============================================================================

The event stream becomes the heartbeat of the platform.

Operational dashboards should display

Events per second

Failed deliveries

Retry queues

Processing latency

Subscriber health

Dead-letter queues

This enables rapid diagnosis of production issues.

==============================================================================
WHEN NOT TO USE EVENTS
==============================================================================

Events are powerful but not universal.

Use synchronous communication when

Immediate user feedback is required.

Validation must occur before continuing.

A query requires an immediate response.

Events should communicate completed business actions.

Not replace every API call.

==============================================================================
ARCHITECT'S NOTES
==============================================================================

The event stream is the nervous system of Lekki.

Business capabilities should remain unaware of one another wherever possible.

They simply perform their responsibilities and announce what has happened.

As the platform grows, new capabilities—including Neo, reporting, machine
learning, partner integrations and future services—can be introduced by
subscribing to existing events rather than modifying existing code.

This architectural style allows Lekki to evolve continuously while preserving
stability, reducing coupling and protecting the integrity of the domain model.
