==============================================================================
PURPOSE
==============================================================================

This document defines how businesses are represented within Lekki.

It establishes the platform's multi-tenant architecture, ownership model,
data isolation strategy, onboarding flow and inheritance rules.

Every commercial customer operates within an Organisation.

Every Organisation owns one or more Venues.

Every Venue delivers one or more Experiences.

Guests move between Organisations.

Data does not.

==============================================================================
ARCHITECTURAL OBJECTIVE
==============================================================================

Lekki must operate as one global platform while ensuring that every customer
feels as though they own their own private system.

The platform should provide

Shared infrastructure

Shared software

Shared innovation

Shared security

while maintaining

Complete business isolation

Independent configuration

Independent reporting

Independent billing

Independent branding

Definition

Venues

==============================================================================
TENANT
==============================================================================

A Tenant is the technical implementation of an Organisation.

Business users should rarely see the word Tenant.

Engineers use Tenant when discussing

Data isolation

Security

Infrastructure

Deployment

Monitoring

Every Organisation maps to exactly one Tenant.

==============================================================================
VENUE
==============================================================================

A Venue is a physical operating location.

Examples

Cape Town Restaurant

Sandton Hotel

Main Festival Grounds

Durban Stadium

Airport Lounge A12

Each Venue inherits configuration from its Organisation but may override
specific settings where permitted.

==============================================================================
LOCATION
==============================================================================

Locations exist inside Venues.

Examples

Restaurant Table

Hotel Room

Festival Zone

VIP Area

Conference Hall

Casino Floor

Gate

Parking Area

The platform treats all Locations equally.

Only Experience Profiles change terminology.

==============================================================================
CONFIGURATION HIERARCHY
==============================================================================

Configuration is inherited downward.

Platform

↓

Organisation Defaults

↓

Venue Overrides

↓

Experience Overrides

↓

Location Overrides

Lower levels inherit unless explicitly overridden.

This reduces duplication while preserving flexibility.

==============================================================================
EXAMPLE
==============================================================================

Platform Language

English

↓

Organisation Default

English + Afrikaans

↓

Venue

English only

↓

VIP Experience

English + French

↓

Location

No Override

Final Result

Inheritance should always be predictable.

==============================================================================
ARCHITECTURAL DECISIONS
==============================================================================

ADR-010-001

One global platform.

Many Organisations.

Reason

Simplifies deployment and continuous innovation.

ADR-010-002

Organisation is the commercial boundary.

Reason

Matches real-world business ownership.

ADR-010-003

Venue inherits from Organisation.

Reason

Reduces duplicated configuration.

ADR-010-004

Guests are global identities.

Reason

One application across every venue.

ADR-010-005

Configuration always preferred over custom software.

Reason

Supports unlimited venue types.

==============================================================================
SUCCESS CRITERIA
==============================================================================

A new Organisation should be capable of

Creating an account

Importing existing data

Configuring branding

Connecting payments

Generating QR Codes

Training staff

Launching operations

within hours rather than weeks.

Neo should reduce onboarding effort to the absolute minimum.

==============================================================================
ARCHITECT'S NOTES
==============================================================================

The Organisation model is the commercial backbone of Lekki.

It defines how customers purchase the platform, how data is protected, how
configuration flows through the hierarchy, and how the SaaS model scales from
a single coffee shop to a global hospitality group.

Every future capability—from Neo to payments to analytics—must respect this
hierarchy. If a feature cannot clearly identify its Organisation, Venue and
ownership boundaries, its design should be reconsidered.
